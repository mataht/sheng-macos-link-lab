# Stage15: GOP display copy-path rebuild

Experimental rebuild of the third-party upstream UFS/GOP driver object with one reviewed change to its CPU-copied
display path. This is a **build experiment**, not an installable image or flashing tool.

## Why

In QEMU, WindowServer animates the spinning wait cursor by recompositing the whole main surface because the GOP
companion advertises no hardware cursor plane. Every frame was then copied in full by the driver: it prepared,
mapped and unmapped the whole root surface, copied each source row to a scratch buffer, wrote every pixel with a
32-bit volatile store and took the pixel lease once per row. The WindowServer thread spent most of its CPU time in
the kernel during that animation.

## Change (display source only)

- `display/gop_scanout.h`: the existing row conversion becomes a template over the destination type (the original
  `nativeGopScanoutRow` keeps its signature and behaviour), plus `nativeGopBlitRows`, which compares each converted
  row with a shadow of what the driver last wrote and rewrites only rows that changed. A refused lease stops the
  frame with the shadow still consistent.
- `display/NativeGOPDisplay.cpp` (generated by `display/0001-native-gop-display.patch` from the pinned DroidVM
  input): new state is appended after every existing member, so existing field offsets are unchanged. Up to three
  root-surface mappings are cached (retained and prepared until evicted). Same-size BGRA rows are compared and
  copied directly from the mapping. The whole frame is rewritten on the first frame, after any geometry or format
  change, and every 300 frames. The periodic report adds rows written and rows left unchanged. The previous row-read
  path remains as a fallback when no mapping is available.
- `IOMobileFramebufferABI.h`, `gop_layers.h`, `swap_wait` handling and all other driver code are unchanged.

## Workflow

`.github/workflows/gop-copy-path.yml` on the `xcode-27` runner:

1. Verifies the overlay hashes in `expected.json` and runs the host tests in `tests/` with Apple clang, ASan and UBSan.
2. Checks out `CrossDarwin/macOS-ForSheng` at `a200d204230846bb640b715086d8c627405ba2df`, fetches its pinned sources,
   verifies the Apple-signed KDK and builds the **unmodified** upstream kernel and UFS/GOP driver, as the upstream
   `macos26-kernel` job does with `native_ufs` and `native_gop`.
3. Records that rebuilt original object and compares it with the upstream CI object
   (`e3fea376…`). Applies the overlay, regenerates the display source with the upstream preparer, re-runs the exact
   recorded compile command for `NativeUfs.o`, and links both objects with the pinned VirtIO object exactly as
   `scripts/link_probe.py` does.

A successful run means the change compiles with the upstream flags (`-Wall -Wextra -Werror`) and links. It does not
establish ABI/PAC compatibility, runtime behaviour or hardware use; those require local admission and a bounded QEMU
run. Upstream authors retain their copyrights; the display source derives from Droid-VM/macOS-DroidVM
(BSD-2-Clause-Patent) via the upstream project. No Apple firmware, KDK, BootKC or device data is committed.
