# 在小米平板 6S Pro（sheng）上运行 macOS 26：技术路线

本文说明本项目在小米平板 6S Pro（代号 sheng，高通 SM8550，国行 16 GB / 1 TB）上运行 macOS 26.5（25F71）的方法：每一层用了什么、为什么这样做，以及哪些已经实测、哪些还没有。当前结果见[移植状态](status.md)。

文中证据分五类：

| 标记 | 含义 |
| --- | --- |
| **实机** | 平板上的录像、照片或二维码读数 |
| **QEMU** | 虚拟机里的运行结果 |
| **CI** | GitHub Actions 里编译、链接通过，没有运行过 |
| **离线** | 读源码、反汇编、主机测试，没有在目标环境运行过 |
| **推断** | 没有直接证据，由已有现象推导 |

## 1. 总体结构

```
fastboot boot（只进内存，不刷写任何分区）
  └─ 安卓启动镜像：UEFI 固件 + 启动盘（FAT）
       └─ UniXNU / DarwinBoot：加载内核、设备树、信任缓存
            └─ 自编译的 XNU 内核 + 苹果原版内核扩展 + 本项目的平台驱动
                 └─ NativeUfs 只读读取 UFS 上的 macOS 分区
                      └─ APFS → launchd → macOS 用户空间
```

原则：

- **不刷写**：平板上的安卓、bootloader 和各固件分区都不动。每次都用 `fastboot boot` 临时启动，重启就回到安卓。
- **macOS 放在独立分区**：只使用 UFS 上新增的分区，不动已有的分区内容。每一次写入都事先列清楚，并由设备主人确认。
- **苹果软件与厂商固件由用户自备**：本项目不分发任何苹果二进制、系统镜像、缓存、信任缓存或厂商固件，CI 也不产出这些文件。**系统镜像由用户自己从苹果官方发布制作，本仓库不提供也不公开制作方法**；厂商固件从平板自己的 Android 分区读取，不随仓库分发。本文只说明启动链对镜像有什么要求。
- **每个驱动默认关闭**：只在启动参数里显式打开，并按级别逐级上机，第 1 级只读。

## 2. 内核

- **来源**：苹果开源的 XNU 12377.121.6（与 25F71 配套），构建 `DEVELOPMENT ARM64` 配置，新增板级配置 `SHENG`。对 XNU 的改动以补丁形式放在 `platform/sheng/macos26/patches/`，按序号应用。
- **平台层**：中断控制器、计时器、多核启动来自 UniXNU 的 ArmCpu / ArmDTPlatform。
  - 8 个核心通过 PSCI 上线，核间中断走 SPI（**实机**）；
  - 内存按 macOS 习惯用 16 KiB 页，开启 arm64e 指针认证（PAC）。
- **缓存维护**：这台机器的 CPU 用 64 位格式报告缓存几何信息（CCSIDR 的 CCIDX 格式，**离线** + **实机**读寄存器）。XNU 里那条“整块按组和路清缓存”的捷径按旧格式解析，在这块 CPU 上基本等于没做，所以显示和 GPU 代码要按地址清缓存。
- **内核集合**：用苹果配套的内核扩展，只挑出需要的（APFS、IOKit 家族、AMFI 等，共 32 个），与本项目的平台驱动一起重新链接成一个内核文件。这一步在本地完成，结果不发布。每次装配都检查：
  - 每个导入符号都必须能解析，不接受弱导入；
  - 我们的驱动派生自苹果类的地方，逐项核对虚函数表的位置和 PAC 元数据（例如 IOHIDDevice 的 334 个槽位）。
- **设备树**：苹果格式的 ADT 由脚本生成，描述 CPU、内存、显示缓冲区、按键、触摸等。

## 3. 存储

- **NativeUfs**：在高通 UFS 控制器上直接发 SCSI 命令的只读驱动（基于 UniXNU）。
  - 只访问事先登记好的分区窗口；
  - 分区开头有一个自描述的头块（SHNGROOT），驱动按头块里的大小和哈希核对后才发布磁盘；
  - 写入默认关闭。
- **内存覆盖层**：系统运行时的写入先进内存，不落盘（恢复系统的 ISC 卷和完整系统各有一套，都有大小上限）。持久写盘已经写好（**离线**），默认关闭，要单独验证、单独开启。
- **日志分区**：运行时保留的日志写入一个小的独立分区，重启后可读回。

## 4. 完整系统对镜像的要求

完整系统用的是一张**用户自备的、已装好的系统镜像**，启动链按下面的条件使用它。镜像怎么得到，不在本项目范围内，本仓库也不公开。

- **按卷 UUID 选根**：设备树的 `root-matching` 填系统卷 UUID，内核加 `-nobsdmgroot`，不让它切到恢复系统的磁盘镜像；
- **开发策略**：dyld 跳过 libignition（Ignition 序列），直接从系统路径加载共享缓存；
- **信任缓存**：系统程序带平台标识，AMFI 要求它们在信任缓存里。本项目把原版信任缓存的条目原样合并成一个模块，由 DarwinBoot 装入内存，普通完整系统包**不加入任何本项目自己的条目**（带 Metal 插件的包见第 7 节）；
- **平台 UUID**：设备树提供固定的 platform UUID，数据卷的挂载流程需要它；
- **压缩文件**：系统文件使用 APFS 压缩（含 LZBITMAP）。原版的压缩扩展会注册这种解压器（**离线**反汇编确认），QEMU 里 dyld 读出了共享缓存（**QEMU**）；
- **位于默认搜索路径之外的库**：跳过 libignition 后，dyld 不知道个别库所在的目录，`loginwindow` 依赖的一个库因此加载失败。除 PID 1 外，每个进程都会切换到共享缓存里的那份 dyld，所以在内存里改共享缓存中这一页代码，设置好路径。修改前后核对原始字节和页哈希，磁盘上的文件不动；
- **平台缺少的服务**：`watchdogd` 需要 `IOWatchdog` 服务，这个内核没有。它崩溃后，内核按“崩溃即 panic”处理，首次实机启动因此在约 6 分钟时停机。现在有两个最小的服务，都由启动参数打开：一个报告看门狗已关闭（`watchdogd` 正常退出），一个只回答状态的 AppleKeyStore（无 keybag、无密码、已解锁）。启动参数还加了 `panic_on_crash_disabled=1`，其他服务崩溃时不再停机；
- **登录**：平板没有实体键盘，所以需要自动登录，而且登录后不能锁屏。系统默认自动登录后会立刻锁屏，这一项偏好要关掉。

证据：完整系统在 QEMU 里连续运行 1 小时（**QEMU**）；在平板上到达登录界面和桌面（**实机**）。NativeUfs 无法在 QEMU 里读 UFS，所以完整系统的长时间 QEMU 证据来自同一次构建的 VirtIO 版本：内核、内核集合、UUID 和模块列表都相同，只有存储驱动不同。UFS 驱动本身要到平板上才算验证。

## 5. 显示

- **NativeGOPDisplay**：bootloader 已经点亮屏幕并留下一块帧缓冲区，我们的驱动把它以 IOMobileFramebuffer 的形式交给 WindowServer（**实机**）。
- **CPU 软件绘制模式（不加载 Metal 插件时）**：WindowServer 默认要 Metal。不带 Metal 插件时（`sheng-full-ui=1`），在内存里修改共享缓存中少数几页代码（SkyLight、QuartzCore 等），让它改走 CPU 合成和 BGRA 输出：
  - 修改前后都核对原始字节和页哈希，磁盘上的系统文件不动；
  - 完整系统用的修改页，从完整系统自己的缓存里按函数名重新推导，找不到或字节不符就停止，不猜。
- **只拷变化的行与按地址清缓存**：每次交换缓冲区时，只把发生变化的行写进屏幕的帧缓冲；因为 CPU 采用 64 位 CCIDX 缓存几何格式，新的显示代码按地址清缓存。这两项都是默认关闭的选项，今晚的 GPU 包都打开了（**实机** / **QEMU**）。
- **按阶段计时与帧缓冲内存带宽（实机测量）**：显示驱动每帧把 WindowServer 交上来的画面拷到屏幕的帧缓冲，每帧大约 0.1 到 0.4 秒，主要花在读取画面、和上一帧比较、把变化的行写进帧缓冲这几步（**实机**）。帧缓冲目前是 Device 内存映射，内存读数器在平板上测到（上机 39，单位 MiB/s，**实机**）：

  | 内存类型 | 写 | 读 |
  | --- | --- | --- |
  | 可缓存 | 约 11236 | 约 10637 |
  | Device | 约 79 | 约 141 |
  | 写合并 | 约 11275 | 约 256 |

  因此整屏变化时，光写帧缓冲就要约 0.3 秒。**推断**：把帧缓冲改成写合并映射会快很多（这是下一步的计划，还没做）。此外，CPU 软件绘制的画面被读取时也很慢，读速约 70 MB/s（**实机**）；**推断**这些画面在内核里是按不可缓存方式映射的。
- **屏幕常亮**：睡眠关闭。QEMU 里系统睡眠会 panic（内核没有完成核心注册）。
- **软件光标**：系统默认想把光标放到硬件平面，而这里只显示根图层，光标会消失，所以在内存里让 SkyLight 强制使用软件光标。
- **启动日志不再滚屏**：启动日志面板原来每出一行就要通过设备映射读写约 100 万个像素，每行约 0.25 秒。改成回绕写入、不读屏幕后，大幅缩短了启动日志阶段的耗时（**实机**）。

## 6. 输入

- **按键**：通过 SPMI 读取 PMIC 的电源键和音量键状态，作为键盘按键（方向键、Tab、回车）上报给 macOS（**实机**）。
- **触摸**：Novatek NT36532E，沿用 UniXNU-sheng 在 iPadOS 上验证过的“主机计算”路线：
  - 每次开机由主机把固件下载进触控芯片；
  - 主机读取电容矩阵帧，自己计算触点；
  - 结果作为单点绝对坐标指针上报给 macOS：手指按下等于左键，在 CPU 软件绘制桌面和 GPU 合成的设置助理页面上都能用（**实机**）。
- **触摸固件不进仓库**：固件从平板自己的 Android 分区读取，在本地打包时写进设备树，不随仓库分发，也不进 CI。
- **键盘保护套**：用 UniXNU-sheng 的 I²C 和 MCU 协议代码，默认关闭，分 5 级（1 只读快照，2 时钟和引擎识别，3 引导 ROM，4 MCU 镜像和帧，5 HID）：
  - 第 1 级（只读，稳压器 L6B、L12B、L13B 读数为关闭）和第 2 级（时钟投票和 I²C 引擎识别，不上电、不通信）在平板上通过（**实机**）。
  - 第 3 级（上机 28，**实机**）是第一次给键盘投电压：通过 RPMh 投 L12B 1.8 V、L13B 3000 mV。时钟和 I²C 引擎和第 2 级一样正常，但给 L12B 的投票在 50 毫秒内没有收到完成信号，驱动按设计在这里停下：L13B 没有投，也没有任何 I²C 通信。13 秒后整机发生一次内核锁等待超时 panic；同样特征的 panic 以前在没有键盘驱动时出现过一次，所以两者有没有关系**没有确定**。
  - **推断**的原因：投票前没有打开那个命令通道的完成中断。修复已经写好（**离线**），还没编译，也没上机。

## 7. GPU

目标是用 Adreno 740 做 Metal 加速。路线是：WindowServer → Metal 插件 → Metal 到 Vulkan 的转换层（metal2vulkan）→ Turnip（Mesa 的 Adreno Vulkan 驱动，带 Darwin 后端）→ 内核的 Adreno 740 驱动。

- **内核**：一个 `IOAccelerator` 子类前端，加 Adreno 740 的电源、SMMU、命令提交代码（基于 UniXNU 的 Adreno740 组件，改成 16 KiB 页）。GPU 固件从平板自己的 Android 分区读取，只从设备树节点里加载，不随仓库分发。
- **用户态与安装路径**（只在 `sheng-gpu-metal=1` 时，默认关闭）：打包时把插件放进设备树节点；第 9 级时驱动把它写进数据卷（数据卷在内存覆盖层后面，不落盘）；信任缓存在苹果原有的条目之外再加插件的两个 CDHash（打包器只接受“原条目加恰好这两个”的缓存），并把 `lp-sip0` 设为 2；`sheng-full-ui=2` 用完整系统的页表，去掉三个把 Metal 关掉的页（不带插件的 `sheng-full-ui=1` 不变）。

已有的结果：

| 阶段 | 结果 | 证据 |
| --- | --- | --- |
| Turnip 在 macOS runner 上构建（arm64e） | 通过，只链接系统库 | **CI** |
| Rust 桥构建（arm64e 指针认证 ABI） | 通过，两次构建字节一致 | **CI** |
| 空插件探针与真插件探针 | QEMU 里 WindowServer 加载了插件并调用初始化；QEMU 没有 A740，真插件按预期回答“没有设备” | **QEMU** |
| 假的 A740（QEMU 专用） | Turnip 创建了设备，提交 2 次，出现首帧（800×600，没有内容，因为假设备不执行任何命令）；之后 WindowServer 偶发异常退出，原因不明 | **QEMU** |
| 内核栈第 1 到 9 级，不带 Metal 插件（含上机 39 对照） | 第 1 级只读；第 3 到 8 级上电、时钟、SMMU 上下文、GMU 固件、GX 上电与心跳正常；第 9 级 TrustZone 三次安全调用（zap 固件加载认证、SMMU 光圈）返回 0，GPU 通过自身 SMMU 上下文执行命令并产生中断（取消映射按 16 KiB 整页执行）。上机 39 同一个内核跑到第 9 级、不带 Metal 插件，快启动并进入 CPU 软件绘制的桌面（壁纸和菜单栏显示） | **实机**（读自录像和照片） |
| 绕开 GPU 挂起（`sheng-gpu-wc=0`） | 此前挂起 panic 的二维码显示：命令处理器停在第一个间接缓冲区的末尾，读到的缓冲区内容是 0，写合并审计发现 16 条脏的或过期的缓存行（**推断**：缓冲区还在 CPU 缓存里，没有写到 DRAM）。把客户端缓冲区改成可缓存并在每次提交前做缓存维护后，GPU 工作能完成，不再挂起 | **实机**（二维码和录像读数） |
| **Metal 插件显示出经 GPU 合成的界面（上机 38）** | 快启动，屏幕**第一次出现了经 GPU 合成的内容**：桌面壁纸、菜单栏（输入法“简体拼音”、日期“11月10日 周二”）、登录后的设置助理页面（先是“自动更新 Mac”，点“继续”后往下走了几页，到第 300 秒设定的诊断 panic 时停在网络设置页）。在这些页面上触摸能用，大约每秒 6 帧。显示驱动在屏幕上 64 个点采样，64 个全有内容（之前带插件黑屏的启动这个数是 0）。第 300 秒的二维码：GPU 收到 759 次提交，完成 758 次，没有 GPU 挂起；有 7 个进程打开过 GPU（二维码里进程名截断，按截断名字**推断**包括 WindowServer、loginwindow、通知中心、设置助理和 iconservicesagent）；IO 一致性探针通过 | **实机**（录像、照片、第 300 秒诊断二维码） |

**还不好的地方（GPU 加速还很慢，不能写成已可用）：**

- **Fence 等待大量超时**：显示驱动每帧最多等 GPU 50 毫秒，大部分帧都等到超时；内核里对 GPU fence 的等待，2274 次中有 1517 次超时（**实机**，第 300 秒诊断二维码和屏幕状态行）。二维码里还有缓存维护耗时等字段，含义还在核对。
- **偶发的慢启动（原因未查清）**：最近 3 次带 Metal 插件的启动（上机 21、33、38）里，有 2 次（上机 21、33）明显变慢。上机 33 从内核开始到 WindowServer 接管屏幕约 104 秒；快的时候（上机 23、38、39）是 22 到 33 秒；更早带插件的上机 15、17 也速度正常，今晚 4 次不带插件的启动全是快的（**实机**，读自录像）。慢启动时测过 CPU 频率，三组核心一直是正常值（约 1670、2707、2956 MHz），排除了 CPU 降频；从上机 33 的录像看，慢的那一段从 `launchd` 启动以后就开始了，那时 WindowServer 还没启动（**实机**）。上机 38 和上机 21、33 是同一类包，为什么它快、能出画面，还不知道。

**许可证说明**：转换层所用的 metal2vulkan 是 GPL-2.0 或更高 / LGPL-3.0 或更高双许可，含 metal2vulkan 的插件包**不分发**（许可证问题还没定）。

## 8. 其他驱动

这些驱动都默认关闭，按级别逐级在平板上验证：

| 驱动 | 内容 | 平板上读到的 |
| --- | --- | --- |
| Wi-Fi（WCN7850） | 电源、PCIe、MHI、固件引导的逐级接入 | 第 1 级：PCIe0 电源域关闭，无时钟投票，WLAN_EN、BT_EN、PERST# 为低。第 2 级：PCIe0 链路建立，读到端点 ID `17cb:1107`（WCN7850）。第 3 级：读到 BAR0（2 MiB）、总线主控已打开、MHI 和 BHI 寄存器，无 panic；MHIVER 读成 `0xdeadbeef`，含义未定。第 4 级（上机 23）：固件已装进 8 MiB 的 DMA 窗口，长度和摘要由内核自己核对正确；Wi-Fi 的 SMMU 数据流已路由好，MHI 和 BHI 的布局也读到了，没有卡住；但这块 SMMU 不支持地址翻译自检（ATOS），所以 DMA 窗口的地址翻译**没有验证过**。第 5 级（上机 26）：执行了芯片上电和 boot loader 的门铃，没有卡住，也没有 panic；结果行要等芯片报“就绪”之后才打印，那时图形界面已经接管了屏幕，所以**第 5 级的结果目前不知道**（要看到结果需要改代码）（以上均**实机**，读自录像）。固件从平板自己的 Android 分区读出，和上游 linux-firmware 不同，仓库里不含任何固件。Wi-Fi 后面没有无线协议栈，离联网还很远 |
| USB | 控制器、PHY、主机角色 | 第 1 级只读状态快照（**实机**）；平板没有 CPU 侧的 VBUS 路径，后面几级需要外部 5 V 供电 |
| ADSP / 电池 | DSP 启动、电池管理服务 | 第 1 级只读 SMEM、SMP2P、AOSS 等状态（**实机**） |
| RTC、背光、内存性能读取 | 实时时钟、背光、L3 和内存带宽测量 | 背光跑过第 1 级只读。RTC 第 2 级：平台专家提前发布 `IORTC`（内核原本会等它最多 30 秒），`NativeRtc` 把日历向前拨到打包时间，启动到 WindowServer 画面约省 30 秒（日历是打包时间，不是真实时间，**实机**）。内存读数器在平板上测得可缓存、Device、写合并三种映射的读写带宽（上机 39，**实机**，见第 5 节） |
| CPU 频率读取 | 周期读取三个核心簇的频率 | 小核约 1670、中核约 2707、大核约 2956 MHz，慢启动时也是正常值，排除了 CPU 降频（**实机**） |

## 9. 验证方法

- **先 QEMU，后实机**：每个内核先在 QEMU 里通过 4 项快速检查（找到根卷、存储驱动默认关闭、内存布局与平板一致、8 核启动）和一次完整的 1200 秒完整系统运行（没有 panic，镜像没变），再打包上机。2026-11-10 晚上平板的每个新内核上机前都有完整的 1200 秒 QEMU 完整系统运行，新显示代码的“只拷变化的行”模式也单独在 QEMU 里跑过一次，同样干净（**QEMU**）。（早先上机 14 到 17 曾在用户逐包放弃该条的前提下启动，完整的运行后来都已补跑通过，见[移植状态 · 验证上的缺口](status.md#5-验证上的缺口)。）
- **观察工具与偶发 panic 处理**：观察工具修了一个问题——运行到时间上限时，虚拟机如果正好停在用户态，最后一次读内核数据就会失败，现在工具会先让虚拟机短暂运行到内核态再读，验收条件没改（**离线** / **QEMU**）。`opendirectoryd` 打开 `/Search` 或 `/Local/Default` 失败的偶发 panic 在 QEMU 里出现时，该次运行重跑，不作为证据。
- **按改动范围分级**：只改显示或输入时，可以沿用参考内核的长时间证据，显示和输入的行为改在实机上看；改了存储、内核补丁或启动链，就必须重新跑。哪些可以沿用，由工具比对构建记录来判定，不靠人工判断。
- **独立复核**：每个启动包另有一个脚本复核，逐字节比较容器、内核、设备树和启动参数，只允许预期的差异。
- **两个构建渠道**：CI（私有仓库）和 macOS 本机（用 Xcode 27.2 构建）。同一源码，本机构建与 CI 内核不逐字节相同（工具链版本不同），所以按新内核处理，各自过门槛。
- **实机操作**：每次重启、启动、写入都要由仓库主人单独批准，只执行一次，不自动重试，发启动命令前读取平板温度，并留下记录。
- **诊断**：开发内核在屏幕上打印启动进度、关键驱动的状态行和显示阶段计时；panic 时屏幕上显示二维码，内含寄存器、栈信息或设定的第 300 秒 GPU 状态诊断数据。

## 10. 已知限制与风险

- **安全设定**：开发内核，根卷不做封印校验，AMFI 开发者模式，没有 SEP。安全性远低于正版 Mac。
- **性能**：GPU 加速第一次出了画面，但每秒只有约 6 帧，显示等待和内核 fence 等待大量超时，且带插件启动偶发变慢；帧缓冲目前为 Device 内存映射（写速约 79 MiB/s），每帧显示拷贝花 0.1 到 0.4 秒；不带插件走 CPU 软件绘制时画面读取（约 70 MB/s）和用户态合成也很慢（见[移植状态](status.md)）。
- **信任缓存**：带 Metal 插件的包在苹果原有的信任缓存条目之外加了插件的两个 CDHash，并把 `lp-sip0` 设为 2；普通完整系统包不这样做。
- **硬件支持**：可用的 GPU 加速、Wi-Fi 联网、蓝牙、USB、键盘保护套、声音、电池状态、摄像头、传感器、亮度、睡眠、持久写盘都还没有。
- **法律**：macOS 及其组件受苹果许可约束。本项目只提供开源代码，不提供苹果软件、厂商固件或含 metal2vulkan 的插件包，也不提供取得苹果软件或制作系统镜像的方法。
