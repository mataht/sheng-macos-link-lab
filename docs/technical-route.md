# 在小米平板 6S Pro（sheng）上运行 macOS 26：技术路线

本文说明本项目在小米平板 6S Pro（代号 sheng，高通 SM8550，国行 16 GB / 1 TB）上运行 macOS 26.5（25F71）的方法：每一层用了什么、为什么这样做，以及哪些已经实测、哪些还没有。当前结果见[移植状态](status.md)。

文中证据分四类：

| 标记 | 含义 |
| --- | --- |
| **实机** | 在平板上观察到的结果 |
| **QEMU** | 在虚拟机里观察到的结果 |
| **CI** | GitHub Actions 里编译、链接通过，没有运行过 |
| **离线** | 只对二进制或源码做过检查，没有运行过 |

## 1. 总体结构

```
fastboot boot（只进内存，不刷写任何分区）
  └─ 安卓启动镜像：UEFI 固件 + 启动盘（FAT）
       └─ UniXNU / DarwinBoot：加载内核、设备树、信任缓存
            └─ 自编译的 XNU 内核 + 苹果原版内核扩展 + 本项目的平台驱动
                 └─ NativeUfs 只读读取 UFS 上的 macOS 分区
                      └─ APFS → launchd → macOS 用户空间
```

原则：

- **不刷写**：平板上的安卓、bootloader 和各固件分区都不动。每次都用 `fastboot boot` 临时启动，重启就回到安卓。
- **macOS 放在独立分区**：只使用 UFS 上新增的分区，不动已有的分区内容。每一次写入都事先列清楚，并由设备主人确认。
- **苹果软件由用户自备**：本项目不分发任何苹果二进制、系统镜像、缓存、信任缓存或固件，CI 也不产出这些文件。**系统镜像由用户自己从苹果官方发布制作，本仓库不提供也不公开制作方法**；本文只说明启动链对镜像有什么要求。
- **每个驱动默认关闭**：只在启动参数里显式打开，并按级别逐级上机，第 1 级只读。

## 2. 内核

- **来源**：苹果开源的 XNU 12377.121.6（与 25F71 配套），构建 `DEVELOPMENT ARM64` 配置，新增板级配置 `SHENG`。对 XNU 的改动以补丁形式放在 `platform/sheng/macos26/patches/`，按序号应用。
- **平台层**：中断控制器、计时器、多核启动来自 UniXNU 的 ArmCpu / ArmDTPlatform。
  - 8 个核心通过 PSCI 上线，核间中断走 SPI（**实机**）；
  - 内存按 macOS 习惯用 16 KiB 页，开启 arm64e 指针认证（PAC）。
- **内核集合**：用苹果配套的内核扩展，只挑出需要的（APFS、IOKit 家族、AMFI 等，共 32 个），与本项目的平台驱动一起重新链接成一个内核文件。这一步在本地完成，结果不发布。每次装配都检查：
  - 每个导入符号都必须能解析，不接受弱导入；
  - 我们的驱动派生自苹果类的地方，逐项核对虚函数表的位置和 PAC 元数据（例如 IOHIDDevice 的 334 个槽位）。
- **设备树**：苹果格式的 ADT 由脚本生成，描述 CPU、内存、显示缓冲区、按键、触摸等。

## 3. 存储

- **NativeUfs**：在高通 UFS 控制器上直接发 SCSI 命令的只读驱动（基于 UniXNU）。
  - 只访问事先登记好的分区窗口；
  - 分区开头有一个自描述的头块（SHNGROOT），驱动按头块里的大小和哈希核对后才发布磁盘；
  - 写入默认关闭。
- **内存覆盖层**：系统运行时的写入先进内存，不落盘（恢复系统的 ISC 卷和完整系统各有一套，都有大小上限）。持久写盘已经写好，默认关闭，要单独验证、单独开启。
- **日志分区**：运行时保留的日志写入一个小的独立分区，重启后可读回。

## 4. 完整系统对镜像的要求

完整系统用的是一张**用户自备的、已装好的系统镜像**，启动链按下面的条件使用它。镜像怎么得到，不在本项目范围内，本仓库也不公开。

- **按卷 UUID 选根**：设备树的 `root-matching` 填系统卷 UUID，内核加 `-nobsdmgroot`，不让它切到恢复系统的磁盘镜像；
- **开发策略**：dyld 跳过 libignition（Ignition 序列），直接从系统路径加载共享缓存；
- **信任缓存**：系统程序带平台标识，AMFI 要求它们在信任缓存里。本项目把原版信任缓存的条目原样合并成一个模块，由 DarwinBoot 装入内存，**不加入任何本项目自己的条目**；
- **平台 UUID**：设备树提供固定的 platform UUID，数据卷的挂载流程需要它；
- **压缩文件**：系统文件使用 APFS 压缩（含 LZBITMAP）。原版的压缩扩展会注册这种解压器（离线反汇编确认），QEMU 里 dyld 读出了共享缓存；
- **位于默认搜索路径之外的库**：跳过 libignition 后，dyld 不知道个别库所在的目录，`loginwindow` 依赖的一个库因此加载失败。除 PID 1 外，每个进程都会切换到共享缓存里的那份 dyld，所以在内存里改共享缓存中这一页代码，设置好路径。修改前后核对原始字节和页哈希，磁盘上的文件不动；
- **平台缺少的服务**：`watchdogd` 需要 `IOWatchdog` 服务，这个内核没有。它崩溃后，内核按“崩溃即 panic”处理，首次实机启动因此在约 6 分钟时停机。现在有两个最小的服务，都由启动参数打开：一个报告看门狗已关闭（`watchdogd` 正常退出），一个只回答状态的 AppleKeyStore（无 keybag、无密码、已解锁）。启动参数还加了 `panic_on_crash_disabled=1`，其他服务崩溃时不再停机；
- **登录**：平板没有实体键盘，所以需要自动登录，而且登录后不能锁屏。系统默认自动登录后会立刻锁屏，这一项偏好要关掉。

证据：完整系统在 QEMU 里连续运行 1 小时（**QEMU**）；在平板上到达登录界面和桌面（**实机**）。NativeUfs 无法在 QEMU 里读 UFS，所以完整系统的长时间 QEMU 证据来自同一次构建的 VirtIO 版本：内核、内核集合、UUID 和模块列表都相同，只有存储驱动不同。UFS 驱动本身要到平板上才算验证。

## 5. 显示

- **NativeGOPDisplay**：bootloader 已经点亮屏幕并留下一块帧缓冲区，我们的驱动把它以 IOMobileFramebuffer 的形式交给 WindowServer（**实机**）。
- **没有 GPU，靠 CPU 绘制**：WindowServer 默认要 Metal。本项目在内存里修改共享缓存中少数几页代码（SkyLight、QuartzCore 等），让它改走 CPU 合成和 BGRA 输出：
  - 修改前后都核对原始字节和页哈希，磁盘上的系统文件不动；
  - 完整系统用的修改页，从完整系统自己的缓存里按函数名重新推导，找不到或字节不符就停止，不猜。
- **只拷变化的行**：每次交换缓冲区时，只把发生变化的行写进屏幕缓冲区，避免旧内容被写回。
- **屏幕常亮**：睡眠关闭。QEMU 里系统睡眠会 panic（内核没有完成核心注册）。
- **软件光标**：系统默认想把光标放到硬件平面，而这里只显示根图层，光标会消失，所以在内存里让 SkyLight 强制使用软件光标。
- **启动日志不再滚屏**：启动日志面板原来每出一行就要通过设备映射读写约 100 万个像素，每行约 0.25 秒。改成回绕写入、不读屏幕后，又去掉了一处固定的 10 秒等待，实机到桌面约 2 分钟（之前光到 WindowServer 就要 5 分钟左右，**实机**）。

## 6. 输入

- **按键**：通过 SPMI 读取 PMIC 的电源键和音量键状态，作为键盘按键（方向键、Tab、回车）上报给 macOS（**实机**）。
- **触摸**：Novatek NT36532E，沿用 UniXNU-sheng 在 iPadOS 上验证过的“主机计算”路线：
  - 每次开机由主机把固件下载进触控芯片；
  - 主机读取电容矩阵帧，自己计算触点；
  - 结果作为单点绝对坐标指针上报给 macOS：手指按下等于左键（**实机**）。
- **触摸固件不进仓库**：固件是厂商文件，只从用户自己的设备上提取，在本地打包时写进设备树。它不进仓库，也不进 CI。
- **键盘保护套**：用 UniXNU-sheng 的 I²C 和 MCU 协议代码，默认关闭，分 5 级（1 只读快照，2 时钟和引擎识别，3 引导 ROM，4 MCU 镜像和帧，5 HID）。第 1 级已在平板上读过；稳压器读数为关，说明保护套没上电，上电的电压设置需要单独确认。

## 7. GPU

目标是用 Adreno 740 做 Metal 加速。路线分内核和用户态两半：

- **内核**：一个 `IOAccelerator` 子类前端，加 Adreno 740 的电源、SMMU、命令提交代码（基于 UniXNU 的 Adreno740 组件，改成 16 KiB 页）。固件只从设备树节点里读，不进仓库。
- **用户态**：WindowServer 通过 Metal 插件找 GPU。插件由三部分组成：Metal 前端、Rust 桥（把 Metal 调用转成 Vulkan）、Turnip（Mesa 的 Adreno Vulkan 驱动，带 Darwin 后端）。
- **信任路径**：插件要被 WindowServer 加载，需要通过库验证和沙盒规则。这条路径在 QEMU 里验证过（**QEMU**）。

已有的结果：

| 阶段 | 结果 | 证据 |
| --- | --- | --- |
| Turnip 在 macOS runner 上构建（arm64e） | 通过，只链接系统库 | **CI** |
| Rust 桥构建（arm64e 指针认证 ABI） | 通过，两次构建字节一致 | **CI** |
| 空插件探针 | QEMU 里 WindowServer 加载了插件，调用了初始化，IOServiceOpen 成功；插件返回空设备后 WindowServer 按预期异常退出 | **QEMU** |
| 真插件 | WindowServer 加载了插件和 Turnip，运行时回答“没有设备”（QEMU 没有 A740），符合预期 | **QEMU** |
| 假的 A740（QEMU 专用） | Turnip 创建了设备，提交 2 次，出现首帧（800×600，没有内容，因为假设备不执行任何命令）；之后 WindowServer 偶发异常退出，原因不明 | **QEMU** |
| 内核栈第 1 级（只读） | 在平板上运行，没有写入，没有渲染 | **实机** |

还没有做到的：任何 GPU 命令执行、AIR 到 Adreno 着色器的编译、任何平板上的渲染。第 2 级以上（电源域、固件、命令环）都没有在平板上运行过。

**许可证说明**：桥所用的 metal2vulkan 是 GPL-2.0 或更高 / LGPL-3.0 或更高双许可，包含它的构建产物只作为 CI 产物存在，**不发布**；在这个许可证问题处理清楚之前，不会有包含它的发布版本。

## 8. 其他驱动

这些驱动都默认关闭，目前只在平板上跑过第 1 级（只读快照）：

| 驱动 | 内容 | 平板上读到的 |
| --- | --- | --- |
| Wi-Fi（WCN7850） | 电源、PCIe、MHI 的逐级接入 | PCIe0 电源域关闭，没有时钟投票；WLAN_EN、BT_EN、PERST# 为低 |
| USB | 控制器、PHY、主机角色 | 只读状态快照；平板没有 CPU 侧的 VBUS 路径，后面几级需要外部 5 V 供电 |
| ADSP / 电池 | DSP 启动、电池管理服务 | 只读 SMEM、SMP2P、AOSS 等状态 |
| RTC、背光、内存性能读取 | 实时时钟、背光、L3 和 DDR 状态读取 | 命令数据库读取成功；其余只读 |
| CPU 频率读取 | 周期读取三个核心簇的频率 | 小核 1670、中核 2707、大核 2956 MHz，说明 CPU 频率不是卡顿的主因 |

## 9. 验证方法

- **先 QEMU，后实机**：每个内核先在 QEMU 里通过一组自动检查，再打包上机：
  - 找到根卷；
  - 存储驱动默认关闭；
  - 内存布局与平板一致；
  - 8 核启动；
  - 必要时跑一次运行到 launchd 主函数的长时间观察（含 ISC 卷）。
- **按改动范围分级**：只改显示或输入时，可以沿用参考内核的长时间证据，显示和输入的行为改在实机上看；改了存储、内核补丁或启动链，就必须重新跑。哪些可以沿用，由工具比对构建记录来判定，不靠人工判断。
- **独立复核**：每个启动包另有一个脚本复核，逐字节比较容器、内核、设备树和启动参数，只允许预期的差异。
- **实机操作**：每次重启、启动、写入都要事先确认，只执行一次，不自动重试，并留下记录。
- **诊断**：开发内核在屏幕上打印启动进度和关键驱动的状态行；panic 时屏幕上显示二维码，内含寄存器和栈信息。触摸、CPU 频率等都有只读的诊断模式。

## 10. 已知限制与风险

- **安全设定**：开发内核，根卷不做封印校验，AMFI 开发者模式，没有 SEP。安全性远低于正版 Mac。
- **性能**：没有 GPU 加速，全靠 CPU 软件绘制；触摸到画面的延迟很大（见[移植状态](status.md)）。
- **硬件支持**：GPU、Wi-Fi、蓝牙、USB、声音、电池状态、摄像头、传感器、亮度、睡眠都还没有。
- **法律**：macOS 及其组件受苹果许可约束。本项目只提供开源代码，不提供苹果软件，也不提供取得苹果软件的方法。
