# 在小米平板 6S Pro（sheng）上运行 macOS 26：技术路线（已归档）

> **项目已归档（2026-11-12）：** 本仓库已停止更新并归档。上游 [UniXNU](https://github.com/UniXNU/UniXNU) 与 [UniXNU-sheng](https://github.com/UniXNU/UniXNU-sheng)（设备页 [unixnu.com/devices/sheng](https://unixnu.com/devices/sheng)）在小米平板 6S Pro（sheng）上已有进度更快的 macOS 实现（已推进到 macOS 27.3，支持 GPU 显示拷贝与直接扫描输出、CPU/GPU 动态调频、Wi-Fi 联网、键盘保护套与触摸板、音频及内核 work interval 补丁等）。本文保留本仓库 macOS 26.5（25F71）实验在归档时的技术路线与实测记录。

本文说明本项目在小米平板 6S Pro（代号 sheng，高通 SM8550，国行 16 GB / 1 TB）上运行 macOS 26.5（25F71）的方法：每一层用了什么、为什么这样做，以及哪些已经实测、哪些在归档时尚未完成。完整状态见[移植状态](status.md)。

文中证据分五类：

| 标记 | 含义 |
| --- | --- |
| **实机** | 平板上的录像、照片、二维码读数或从实机分块扫描提取的崩溃报告 |
| **QEMU** | 虚拟机里的运行结果 |
| **CI** | GitHub Actions 里编译、链接通过，没有运行过 |
| **离线** | 读源码、反汇编、主机测试，没有在目标环境运行过 |
| **推断** | 没有直接证据，由已有现象推导 |

## 1. 总体结构

```
fastboot boot（只进内存，不刷写启动和固件分区）
  └─ 安卓启动镜像：UEFI 固件 + 启动盘（FAT）
       └─ UniXNU / DarwinBoot：加载内核、设备树、信任缓存
            └─ 自编译的 XNU 内核 + 苹果原版内核扩展 + 本项目的平台驱动
                 └─ NativeUfs 读取或持久写入 UFS 上登记好的 macOS 分区窗口
                      └─ APFS → launchd → macOS 用户空间（Metal 插件 → Turnip → Adreno 740）
```

原则：

- **不刷写启动与固件分区**：平板上的安卓、bootloader 和各固件分区都不动。每次都用 `fastboot boot` 临时启动；在 macOS 苹果菜单点击“重启”（或强制重启）即可回到安卓，点击“关机”即可正常关机（**实机**）。
- **macOS 放在独立分区，写入严格受限**：只使用 UFS 上新增的分区，不动已有的分区内容。持久写盘只允许写入 `macossystem` 分区内的 OS 窗口，窗口外一切区域（含分区开头的 `SHNGROOT` 清单块、GPT、`macosroot`）只读不动，每次上机后可通过 TWRP 分块哈希扫描核对并按需还原（**实机** / **离线**）。
- **苹果软件与厂商固件由用户自备**：本项目不分发任何苹果二进制、系统镜像、缓存、信任缓存或厂商固件，CI 也不产出这些文件。**系统镜像由用户自己从苹果官方发布制作，本仓库不提供也不公开制作方法**；厂商固件从平板自己的 Android 分区读取，不随仓库分发。本文只说明启动链对镜像有什么要求。
- **每个驱动默认关闭**：只在启动参数里显式打开，并按级别逐级上机，第 1 级只读。

## 2. 内核

- **来源**：苹果开源的 XNU 12377.121.6（与 25F71 配套），构建 `DEVELOPMENT ARM64` 配置，新增板级配置 `SHENG`。对 XNU 的改动以补丁形式放在 `platform/sheng/macos26/patches/`，按序号应用。
- **平台层**：中断控制器、计时器、多核启动来自 UniXNU 的 ArmCpu / ArmDTPlatform。
  - 8 个核心通过 PSCI 上线，核间中断走 SPI（**实机**）；
  - 内存按 macOS 习惯用 16 KiB 页，开启 arm64e 指针认证（PAC）；
  - 支持 PSCI 复位与关机钩子（`sheng-psci-reset=1`），在平板上从 macOS 菜单点击“重启”可干净卸载卷并复位回到安卓，点击“关机”可干净卸载卷并关机（上机 49、50，**实机**）。
- **缓存维护**：这台机器的 CPU 用 64 位格式报告缓存几何信息（CCSIDR 的 CCIDX 格式，**离线** + **实机**读寄存器）。XNU 里那条“整块按组和路清缓存”的捷径按旧格式解析，在这块 CPU 上基本等于没做，所以显示和 GPU 代码要按地址清缓存。
- **内核集合**：用苹果配套的内核扩展，只挑出需要的（APFS、IOKit 家族、AMFI 等，共 32 个），与本项目的平台驱动一起重新链接成一个内核文件。这一步在本地完成，结果不发布。每次装配都检查：
  - 每个导入符号都必须能解析，不接受弱导入；
  - 我们的驱动派生自苹果类的地方，逐项核对虚函数表的位置和 PAC 元数据（例如 IOHIDDevice 的 334 个槽位）。
- **设备树**：苹果格式的 ADT 由脚本生成，描述 CPU、内存、显示缓冲区、按键、触摸等。

## 3. 存储

- **NativeUfs**：在高通 UFS 控制器上直接发 SCSI 命令的存储驱动（基于 UniXNU）。
  - 只访问事先登记好的分区窗口；
  - 分区开头有一个自描述的头块（`SHNGROOT`），驱动按头块里的大小和哈希核对后才发布磁盘；
  - 写入默认关闭，可通过启动参数选择内存覆盖层模式或持久写盘模式。
- **内存覆盖层模式与写盘分析**：不开启持久写盘时，系统运行期写入先进内存，关机即丢。上机 44 使用 2048 MiB 覆盖层在桌面运行约 5.5 分钟后因写满而 panic；离线查明原覆盖层使用的 `IOMalloc(4096)` 位于 XNU 的 zone map（上限为内核内存的 37.5%，即 4.5 GiB）。改用从 zone map 之外分配 1 MiB 锁定块的独立页池（`native-ufs-root-overlay-pool=1`，上限 4096 MiB）并在上机 47 运行到 1140 秒输出写盘报告后查明：前 6 分钟会集中写入约 2 GiB，之后 800 秒只写约 250 MiB，主要写入者为系统缓存服务（`coresymbolicationd` 1885 MiB、`iconservicesd` 392 MiB、`mediaanalysisd` 385 MiB、`iconservicesagent` 198 MiB、`corespotlightd` 130 MiB）（**实机**）。这些缓存正是持久系统跨重启保留的内容，而 2.3 GiB 的内存覆盖层池会把空闲内存挤到只剩 65 MiB，因此日常运行应走持久写盘。
- **持久写盘模式（`native-ufs-root-writes=1`，已在实机验证）**：
  - **边界保护**：`RootLayout` 与 `RootCommands` 在每次写寄存器前双重检查目标为 LUN 0 且偏移落在 `macossystem` 的 OS 窗口内，排除 `SHNGROOT` 头块和前 1 MiB（离线 21 项故障注入变异测试抓获 20 项，另 1 项在未打开窗口时无行为变化，**离线**）。
  - **分块扫描、还原与离线校验工具**：把 OS 窗口按 7630 个 8 MiB 块管理。在 TWRP 里只读扫描全部块哈希、主备 GPT、`SHNGROOT` 头块、窗口外空白区和 `macosroot`，只拉取发生变化的块；需要还原时只把哈希不同的块写回；离线工具把变化的块叠在基准镜像上，执行 APFS Fletcher-64 校验并从 Data 卷提取日志和崩溃报告（**离线** + **实机**）。
  - **实机结果（上机 46、48、49、50）**：四次持久启动分别改写了 383、500、589、593 个 8 MiB 块（最高约 2.59 GB），窗口外所有区域 0 改动；四次启动后的 APFS Fletcher-64 校验均为 **0 失败**（主容器检查点 `xid` 从 12808 依次推进到 13104、13409、13986、14318，验证对象最高 1008 个，其中上机 49 点菜单“重启”、上机 50 点菜单“关机”均干净卸载了 Data 与 Update 卷），并从 Data 卷成功提取出 1266 个文件（**实机**）。
- **日志分区**：早期启动阶段保留的日志写入一个小的独立分区，重启后可读回。

## 4. 完整系统对镜像的要求

完整系统用的是一张**用户自备的、已装好的系统镜像**，启动链按下面的条件使用它。镜像怎么得到，不在本项目范围内，本仓库也不公开。

- **按卷 UUID 选根**：设备树的 `root-matching` 填系统卷 UUID，内核加 `-nobsdmgroot`，不让它切到恢复系统的磁盘镜像；
- **开发策略**：dyld 跳过 libignition（Ignition 序列），直接从系统路径加载共享缓存；
- **信任缓存**：系统程序带平台标识，AMFI 要求它们在信任缓存里。本项目把原版信任缓存的条目原样合并成一个模块，由 DarwinBoot 装入内存，普通完整系统包**不加入任何本项目自己的条目**（带 Metal 插件的包见第 7 节）；
- **平台 UUID**：设备树提供固定的 platform UUID，数据卷的挂载流程需要它；
- **压缩文件**：系统文件使用 APFS 压缩（含 LZBITMAP）。原版的压缩扩展会注册这种解压器（**离线**反汇编确认），QEMU 里 dyld 读出了共享缓存（**QEMU**）；
- **位于默认搜索路径之外的库**：跳过 libignition 后，dyld 不知道个别库所在的目录，`loginwindow` 依赖的一个库因此加载失败。除 PID 1 外，每个进程都会切换到共享缓存里的那份 dyld，所以在内存里改共享缓存中这一页代码，设置好路径。修改前后核对原始字节和页哈希，磁盘上的文件不动；
- **平台缺少的服务**：`watchdogd` 需要 `IOWatchdog` 服务，这个内核没有。它崩溃后，内核按“崩溃即 panic”处理，首次实机启动因此在约 6 分钟时停机。现在有两个最小的服务，都由启动参数打开：一个报告看门狗已关闭（`watchdogd` 正常退出），一个只回答状态的 AppleKeyStore（无 keybag、无密码、已解锁）。启动参数还加了 `panic_on_crash_disabled=1`，其他服务崩溃时不再停机；
- **自动登录、不锁屏与关闭设置助理**：平板没有实体键盘，所以需要自动登录，并关掉“自动登录后立刻锁屏”的偏好（`autoLoginUserScreenLocked=false`）；此外，用户目录下 `com.apple.loginwindow.plist` 中的 `MiniBuddyLaunch` 需设为 `false`，否则每次登录后会弹出设置助理并卡在网络页（修改后直接进入完整桌面，**实机**）。
- **实机崩溃报告揭示的用户态与内核配合缺口**：
  - **拖动滚动条崩溃**：系统设置、通用设置扩展和聚焦搜索（Spotlight）在拖动或点击滚动条时崩溃，从实机 Data 卷提取的 `.ips` 报告显示 `-[NSScroller mouseDown:]` → `trackKnob:` → `-[NSScrollView _informDelegateWillStartLiveScroll]` → `NSUpdateCyclePerfSectionRegulationBegin` → AppKit `PerfRegulatorStart` 因 `Failed to create performance regulator work interval (error %i).` 主动调用 `abort`（**实机**）。这需要内核补齐 work interval 支持（上游 `UniXNU` 已有对应补丁）。
  - **Safari 图标缺失**：离线检查确认所使用的 26.5 系统镜像未安装 AppOS cryptex，指向 `/System/Cryptexes/App` 的 17 个符号链接（含 `Safari.app`）悬空（**离线**）。

## 5. 显示

- **NativeGOPDisplay**：bootloader 已经点亮屏幕并留下一块帧缓冲区，我们的驱动把它以 IOMobileFramebuffer 的形式交给 WindowServer（**实机**）。
- **CPU 软件绘制模式（不加载 Metal 插件时）**：WindowServer 默认要 Metal。不带 Metal 插件时（`sheng-full-ui=1`），在内存里修改共享缓存中少数几页代码（SkyLight、QuartzCore 等），让它改走 CPU 合成和 BGRA 输出：
  - 修改前后都核对原始字节和页哈希，磁盘上的系统文件不动；
  - 完整系统用的修改页，从完整系统自己的缓存里按函数名重新推导，找不到或字节不符就停止，不猜。
- **只拷变化的行与按地址清缓存**：每次交换缓冲区时，只把发生变化的行写进屏幕的帧缓冲；因为 CPU 采用 64 位 CCIDX 缓存几何格式，新的显示代码按地址清缓存。这两项在 GPU 启动包中均已开启（**实机** / **QEMU**）。上机 49、50 还验证了去掉顶部 4 行诊断状态条的纯净桌面模式（**实机**）。
- **按阶段计时与帧缓冲内存带宽（实机测量）**：显示驱动每帧把 WindowServer 交上来的画面拷到屏幕的帧缓冲。在上机 43 单命令环 GPU 桌面下，GPU 完成很快（客户端等 fence 平均仅 1.5 毫秒），而**显示驱动的 CPU 拷贝占了每帧 0.36 到 0.40 秒（每秒约 2.5 到 3 帧），成为本仓库桌面帧率的瓶颈**（**实机**）：
  - 大多数采样帧在“读取 24.8 MB 画面并与上一帧比较”这一步花 330 到 368 毫秒（读取速率约 75 MB/s），只有两个采样帧在 52 到 55 毫秒内完成了读取比较并写出 223 行（读取速率至少约 475 MB/s，**实机**）；**推断**慢帧读到的是不可缓存映射的表面页，快帧读到的是可缓存映射。
  - 源码复核确认 `NativeGOPDisplay` 已使用 `kIOMapWriteCombineCache` 请求映射启动帧缓冲，但 XNU 的 `wimg_to_pte` 仅在物理地址落在已登记 DRAM 区间（`is_dram_addr(pa)`）时才赋予真正的写合并属性，否则退回设备属性（**离线**）。内存读数器在平板上测到三种映射的读写带宽如下（上机 39，单位 MiB/s，**实机**）：

    | 内存类型 | 写 | 读 |
    | --- | --- | --- |
    | 可缓存 | 约 11236 | 约 10637 |
    | Device | 约 79 | 约 141 |
    | 写合并 | 约 11275 | 约 256 |

- **屏幕常亮**：睡眠关闭。QEMU 里系统睡眠会 panic（内核没有完成核心注册）。
- **软件光标**：系统默认想把光标放到硬件平面，而这里只显示根图层，光标会消失，所以在内存里让 SkyLight 强制使用软件光标。
- **启动日志不再滚屏**：启动日志面板原来每出一行就要通过设备映射读写约 100 万个像素，每行约 0.25 秒。改成回绕写入、不读屏幕后，大幅缩短了启动日志阶段的耗时（**实机**）。

## 6. 输入

- **按键**：通过 SPMI 读取 PMIC 的电源键和音量键状态，作为键盘按键（方向键、Tab、回车）上报给 macOS（**实机**）。
- **触摸**：Novatek NT36532E，沿用 UniXNU-sheng 在 iPadOS 上验证过的“主机计算”路线：
  - 每次开机由主机把固件下载进触控芯片；
  - 主机读取电容矩阵帧，自己计算触点；
  - 结果作为单点绝对坐标指针上报给 macOS：手指按下等于左键，在 GPU 合成桌面、菜单栏、程序坞和各应用窗口内均可用（**实机**）；
  - **点击与拖动判定**：实机测试查明，手指从按下到抬起之间若有轻微移动，上报坐标随之变化，会导致菜单项把手指点击当成拖动；在上机 49、50 中，从苹果菜单点“重启”和“关机”均已验证成功，用电源键（映射为回车）选择“关于本机”也能正常打开窗口（**实机**）。
- **触摸固件不进仓库**：固件从平板自己的 Android 分区读取，在本地打包时写进设备树，不随仓库分发，也不进 CI。
- **键盘保护套**：用 UniXNU-sheng 的 I²C 和 MCU 协议代码，默认关闭，分 5 级（1 只读快照，2 时钟和引擎识别，3 引导 ROM，4 MCU 镜像和帧，5 HID）：
  - 第 1 级（只读，稳压器 L6B、L12B、L13B 读数为关闭）和第 2 级（时钟投票和 I²C 引擎识别，不上电、不通信）在平板上通过（**实机**）。
  - 第 3 级（上机 28，**实机**）第一次给键盘投电压（通过 RPMh 投 L12B 1.8 V、L13B 3000 mV）：时钟和 I²C 引擎正常，但给 L12B 的投票在 50 毫秒内没有收到完成信号，驱动按设计停下（L13B 未投，无 I²C 通信）。13 秒后整机发生一次内核锁等待超时 panic（与无键盘驱动时的上机 03、45 特征相同，是否有因果关系**没有确定**）。
  - **推断**的原因：投票前没有打开那个命令通道（TCS 2）的完成中断（`IRQ_ENABLE` 第 2 位）。修复（投票前打开 `IRQ_ENABLE` 第 2 位、同时接受 `IRQ_STATUS` 或 `CMD_STATUS` 完成标志、I²C 通信前经 SPMI 确认 PMIC 电压已开启）已在本地分支写好并通过主机测试与 QEMU 验证（**离线** / **QEMU**），因项目归档未再上机。

## 7. GPU

目标是用 Adreno 740 做 Metal 加速。路线是：WindowServer → Metal 插件 → Metal 到 Vulkan 的转换层（metal2vulkan）→ Turnip（Mesa 的 Adreno Vulkan 驱动，带 Darwin 后端）→ 内核的 Adreno 740 驱动。

- **内核**：一个 `IOAccelerator` 子类前端，加 Adreno 740 的电源、SMMU、命令提交代码（基于 UniXNU 的 Adreno740 组件，改成 16 KiB 页）。GPU 固件从平板自己的 Android 分区读取，只从设备树节点里加载，不随仓库分发。
- **用户态与安装路径**（只在 `sheng-gpu-metal=1` 时，默认关闭）：打包时把插件放进设备树节点；第 9 级时驱动把它写进数据卷；信任缓存在苹果原有的条目之外再加插件的两个 CDHash（打包器只接受“原条目加恰好这两个”的缓存），并把 `lp-sip0` 设为 2；`sheng-full-ui=2` 用完整系统的页表，去掉三个把 Metal 关掉的页（不带插件的 `sheng-full-ui=1` 不变）。

已有的结果：

| 阶段 | 结果 | 证据 |
| --- | --- | --- |
| Turnip 与 Rust 桥构建（arm64e） | Turnip 只链接系统库；Rust 桥两次构建字节一致 | **CI** |
| QEMU 探针与假的 A740 | WindowServer 加载插件并调用初始化；假 A740 上 Turnip 创建设备并提交首帧（800×600，无内容） | **QEMU** |

**归档时尚未解决的地方：**

- **实机未启用 GPU 温控和动态调频（DCVS）**：已上机包固定跑在 401 MHz（第 4 档；打包器接受 2 到 6 档即 295 到 550 MHz）。
- **照片应用（Photos）打开崩溃**：实机提取的 `.ips` 报告显示，在 `PXGMetalRenderer _setupMetalIfNeeded` 中调用 `PXGMetalTextureConverter createTextureFromCGImage` / `_createTransparentTexture` 时，`PXCreateContext` 断言失败退出（**实机**）；**推断**是 Metal 插件栈缺少某项纹理位图上下文能力。
- **双命令环切换问题与偶发慢启动**：双命令环（默认抢占开启）下点开 App Store 会卡在第二个环的 `CP_BLIT` 上，靠单命令环（`sheng-gpu-preempt=0`）规避；早期带插件的上机 21、33 曾出现慢启动（从 `launchd` 启动后开始变慢，CPU 频率正常），原因尚未查清。

## 9. 验证方法

- **先 QEMU，后实机**：每个内核先在 QEMU 里通过 4 项快速检查（找到根卷、存储驱动默认关闭、内存布局与平板一致、8 核启动）和一次完整的 1200 秒完整系统运行（没有 panic，镜像没变），再打包上机。2026-11-10 晚至 11-11 凌晨上平板的每个新内核上机前都有完整的 1200 秒 QEMU 完整系统运行，新显示代码的“只拷变化的行”模式也单独在 QEMU 里跑过一次，同样干净（**QEMU**）。（早先上机 14 到 17 曾在用户逐包放弃该条的前提下启动，完整的运行后来都已补跑通过，见[移植状态 · 验证上的缺口](status.md#5-验证上的缺口)。）
- **观察工具与偶发 panic 处理**：观察工具修了一个问题——运行到时间上限时，虚拟机如果正好停在用户态，最后一次读内核数据就会失败，现在工具会先让虚拟机短暂运行到内核态再读，验收条件没改（**离线** / **QEMU**）。`opendirectoryd` 打开 `/Search` 或 `/Local/Default` 失败的偶发 panic 在 QEMU 里出现时，该次运行重跑，不作为证据。
- **按改动范围分级**：只改显示或输入时，可以沿用参考内核的长时间证据，显示和输入的行为改在实机上看；改了存储、内核补丁或启动链，就必须重新跑。哪些可以沿用，由工具比对构建记录来判定，不靠人工判断。
- **独立复核**：每个启动包另有一个脚本复核，逐字节比较容器、内核、设备树和启动参数，只允许预期的差异。
- **两个构建渠道**：CI（私有仓库）和 macOS 本机（用 Xcode 27.2 构建）。同一源码，本机构建与 CI 内核不逐字节相同（工具链版本不同），所以按新内核处理，各自过门槛。
- **实机操作与持久写盘审计**：每次重启、启动、TWRP 扫描或写入都要由仓库主人单独批准，只执行一次，不自动重试。持久写盘模式下，每次启动后可在 TWRP 中做只读分块哈希扫描，验证 OS 窗口外 0 改动，并用离线工具校验全部 APFS 容器和对象的 Fletcher-64 校验和、提取 Data 卷上的崩溃报告与日志（**实机** / **离线**）。

## 10. 已知限制与风险

- **安全设定**：开发内核，根卷不做封印校验，AMFI 开发者模式，没有 SEP。安全性远低于正版 Mac。
- **温控与性能**：实机上未运行温度传感器（TSENS）驱动、超温保护和 CPU/GPU 动态调频（DCVS）；桌面帧率受每帧 0.36 到 0.40 秒的 CPU 显示拷贝限制，每秒约 2.5 到 3 帧（见[移植状态](status.md)）。
- **用户态与应用兼容性**：拖动滚动条会因内核缺少 work interval 支持而触发 AppKit 主动中止；照片应用因纹理位图上下文断言失败退出；系统镜像未装 AppOS cryptex 导致 Safari 等悬空；`mobileactivationd` 和 `apsd` 约每 10 秒崩溃重启一次。
- **信任缓存**：带 Metal 插件的包在苹果原有的信任缓存条目之外加了插件的两个 CDHash，并把 `lp-sip0` 设为 2；普通完整系统包不这样做。
- **硬件支持**：本仓库中 Wi-Fi 联网、蓝牙、键盘保护套、USB、声音、电池状态、摄像头、传感器、亮度调节、睡眠都还未在实机跑通。
- **法律**：macOS 及其组件受苹果许可约束。本项目只提供开源代码，不提供苹果软件、厂商固件或含 metal2vulkan 的插件包，也不提供取得苹果软件或制作系统镜像的方法。
