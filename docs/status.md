# 移植状态

更新：2026-11-10 晚（北京时间）。目标设备是小米平板 6S Pro（sheng，SM8550，国行 16 GB / 1 TB），系统是 macOS 26.5（25F71）。

这是实验项目，不适合日常使用。本页只写已经观察到的结果，每条标明证据来源，没做过的写“未做”。

**先说清楚两件事：**

- **GPU 加速第一次在平板上出了画面，但还很慢，不能当成已可用。** 带 Metal 插件启动（上机 38）在屏幕上显示出了经 GPU 合成的桌面壁纸、菜单栏和登录后的设置助理页面，触摸可用，每秒约 6 帧（**实机**）。但显示驱动每帧 50 毫秒的 GPU 等待大部分超时，内核里对 GPU fence 的等待 2274 次中有 1517 次超时，每帧显示拷贝花 0.1 到 0.4 秒，而且带插件启动偶尔会变慢（原因未查清）。
- **每个新内核上机前都有完整的 1200 秒 QEMU 完整系统运行。** 早先的上机 14 到 17 是在没有完整的 QEMU 完整系统运行、由用户逐包放弃这一条的前提下启动的，那些完整运行后来都已经补上并通过。详见[第 5 节](#5-验证上的缺口)。

| 标记 | 含义 |
| --- | --- |
| **实机** | 平板上的录像、照片或二维码读数 |
| **QEMU** | 虚拟机里的运行结果 |
| **CI** | GitHub Actions 的编译和链接通过，没有运行过 |
| **离线** | 读源码、反汇编、主机测试，没有在目标环境运行过 |
| **推断** | 没有直接证据，由已有现象推导 |

## 2. 现在的问题

- **GPU 加速还很慢，fence 等待大量超时**：上机 38 带 Metal 插件第一次在平板上出了画面，但每秒只有约 6 帧（**实机**）。显示驱动每帧最多等 GPU 50 毫秒，大部分帧都等到超时；第 300 秒的诊断二维码显示，内核里对 GPU fence 的等待 2274 次中有 1517 次超时（**实机**）。
- **带 Metal 插件时偶发慢启动（原因未查清）**：最近 3 次带 Metal 插件的启动（上机 21、33、38）里，有 2 次（上机 21、33）明显变慢。上机 33 从内核开始到 WindowServer 接管屏幕约 104 秒；快的时候（上机 23、38、39）是 22 到 33 秒（**实机**，读自录像）。更早带插件的上机 15、17 速度正常，今晚 4 次不带插件的启动也全是快的（**实机**）。慢启动时测过 CPU 频率，三组核心一直是正常值（约 1670、2707、2956 MHz），排除了 CPU 降频；从上机 33 的录像看，慢的那一段从 `launchd` 启动以后就开始了，那时 WindowServer 还没启动（**实机**）。上机 38 和上机 21、33 是同一类包，为什么上机 38 快、能出画面，还不知道。
- **显示拷贝和画面读取慢**：显示驱动每帧把 WindowServer 交上来的画面拷到屏幕的帧缓冲，按阶段计时显示每帧约 0.1 到 0.4 秒，主要花在读取画面、和上一帧比较、把变化的行写进帧缓冲这几步（**实机**）。帧缓冲目前是 Device 内存映射，内存读数器在平板上测得（上机 39，**实机**）：Device 写约 79 MiB/s、读约 141 MiB/s，可缓存写约 11236 MiB/s、读约 10637 MiB/s，写合并写约 11275 MiB/s、读约 256 MiB/s。整屏变化时，光写帧缓冲就要约 0.3 秒；**推断**改成写合并映射会快很多（下一步计划，还没做）。此外，CPU 软件绘制的画面被读取时也很慢，读速约 70 MB/s（**实机**），**推断**这些画面在内核里是按不可缓存方式映射的；不带 GPU 插件时，用户态软件合成也很慢，触摸到画面的延迟很大。
- **键盘保护套第 3 级电压投票没有完成，随后 panic**：第 3 级（上机 28）第一次给键盘投电压（通过 RPMh 投 L12B 1.8 V、L13B 3000 mV），给 L12B 的投票在 50 毫秒内没有收到完成信号，驱动按设计停下（L13B 没投，无 I²C 通信）；13 秒后整机发生内核锁等待超时 panic（**实机**）。同样特征的 panic 以前在没有键盘驱动时出现过一次，两者有没有关系**没有确定**。投票未完成的原因**推断**是投票前没有打开那个命令通道的完成中断；修复已写好（**离线**），还没编译和上机。
- **Wi-Fi 第 5 级结果未知，没有无线协议栈**：第 4 级（上机 23）的 SMMU 不支持地址翻译自检（ATOS），DMA 窗口的地址翻译**没有验证过**；第 5 级（上机 26）执行了芯片上电和 boot loader 门铃，没有卡住也没有 panic，但结果行要等芯片报“就绪”之后才打印，那时图形界面已经接管了屏幕，所以**第 5 级的结果目前不知道**，需要改代码才能看到（**实机**）。Wi-Fi 驱动后面没有无线协议栈，离联网还很远。
- **长时间稳定性没测过**。
- **根分区只读**：系统运行时的写入进内存覆盖层，关机即丢。持久写盘代码已经写好（**离线**），默认关闭，还没有在平板上验证。
- 蓝牙、USB、声音、电池状态、亮度调节、睡眠都还不能用。

## 3. 按功能区域

分级沿用 [UniXNU 设备记录](https://unixnu.com/porting/records)的写法：`planned`（只有计划）、`implemented`（有实现，有源码依据）、`host-verified`（在主机或 QEMU 里验证）、`device-verified`（在平板上验证）。同一区域里不同的部分可能处在不同级别，所以“限制”一栏写明范围。

## 4. 平板上运行过的内容和范围

- 每次都是 `fastboot boot`，镜像只进内存，不刷写分区，重启回到安卓。每次上机都由仓库主人单独批准。
- 系统卷使用内存覆盖层，运行期写入不落盘。
- 驱动默认全部关闭，只在启动参数里显式打开。
- 触摸驱动的 1 到 4 级都在平板上跑过（第 2 级起写时钟投票和引脚配置，第 4 级下载触摸固件）。
- GPU 跑到第 9 级，并运行过带 Metal 插件的启动（上机 38 显示出经 GPU 合成的界面）和不带插件的对照启动（上机 39）；显示驱动跑过只拷变化的行、按地址清缓存和按阶段计时；RTC 跑过第 2 级（发布日历）；内存读数器跑过带宽测量阶段；Wi-Fi 跑到第 5 级；键盘保护套跑到第 3 级（第一次投电压）。
- 其余新驱动（USB、ADSP/电池、背光）在平板上只跑过第 1 级（只读快照），第 2 级以上还没有在平板上执行过。
- 带 Metal 插件的包在苹果原有的信任缓存条目之外，加了插件的两个 CDHash，并把 `lp-sip0` 设为 2；普通完整系统包不变。

## 5. 验证上的缺口

- **今晚上机内核的 QEMU 验证（已满足）**：2026-11-10 晚上平板的每个新内核，上机前都有一次完整的 1200 秒 QEMU 完整系统运行，没有 panic，镜像没变；新显示代码的“只拷变化的行”模式也单独在 QEMU 里跑过一次，同样干净（**QEMU**）。
- **观察工具修复**：原来运行到时间上限时，如果虚拟机正好停在用户态，最后一次读内核数据就会失败。现在观察工具会先让虚拟机短暂运行到内核态再读取，验收条件没有改（**离线** / **QEMU**）。
- **早先上机 14 到 17 的豁免与补跑**：2026-11-09 夜到 11-10 凌晨，第二版集成内核的头三个启动包（上机 14 到 16）和第一个本机构建诊断内核的启动包（上机 17）是在还没有完成 1200 秒 QEMU 完整系统运行、由用户逐包明确放弃这一条的前提下启动的（其余检查如 4 项快速门槛、字节级独立复核、不刷写分区、单独批准均未放宽）。完整的 1200 秒运行后来都已经补跑并通过（**QEMU**）。
- **QEMU 里 `opendirectoryd` 的偶发 panic**：`opendirectoryd` 打开 `/Search` 或 `/Local/Default` 失败时会触发用户态 panic（`panic_on_crash_disabled` 挡不住它）。在客户机日志读得到的 7 次运行里，每次都有 1 到 5 次“重连 5 秒超时”，之后进程重启并成功；不同的只是结局，有时是重启，有时是 panic，原因没有查清（**QEMU** / **离线**）。2026-11-10 当天在 QEMU 里又出现过 3 次，出现的那几次运行都重跑了，不作为证据。平板上没有见过这种 panic。
- **打包器的缺口**：打包器原来不会拒绝以 panic 结束的 QEMU 运行。修复已经写在本地分支，还没并入主线（**离线**）。
