# 移植状态（已归档）

> **项目已归档（2026-11-12）：** 本仓库已停止更新并归档。上游 [UniXNU](https://github.com/UniXNU/UniXNU) 与 [UniXNU-sheng](https://github.com/UniXNU/UniXNU-sheng)（设备页 [unixnu.com/devices/sheng](https://unixnu.com/devices/sheng)）在小米平板 6S Pro（sheng）上已有进度更快的 macOS 实现（已推进到 macOS 27.3，支持 GPU 显示拷贝与直接扫描输出、CPU/GPU 动态调频、Wi-Fi 联网、键盘保护套与触摸板、音频及内核 work interval 补丁等）。本页保留本仓库 macOS 26.5（25F71）实验在归档时的最终状态与实测记录。

更新：2026-11-12（北京时间）。目标设备是小米平板 6S Pro（sheng，SM8550，国行 16 GB / 1 TB），系统是 macOS 26.5（25F71）。

这是实验项目，不适合日常使用。本页只写已经观察到的结果，每条标明证据来源，没做过的写“未做”。

**先说清楚两件事：**

- **完整系统已进入经 GPU 合成的 macOS 桌面并跑通持久写盘、重启与关机，但本仓库归档时还没有在实机启用温控和动态调频，且帧率受显示拷贝限制。** 把 GPU 自身缓冲改走 IO 一致路径、频率提到 401 MHz、改用单命令环（`sheng-gpu-preempt=0`）并关掉设置助理偏好后，平板直接进入经 GPU 合成的完整桌面（壁纸、菜单栏、小组件、程序坞），可打开访达（含全屏）、备忘录、系统设置、App Store、关于本机（用电源键确认）等应用，客户端等 GPU fence 平均仅约 1.5 毫秒（**实机**）。开启 UFS 根分区持久写盘（`native-ufs-root-writes=1`）后，连续四次实机启动（上机 46、48、49、50，含从苹果菜单点“重启”回到安卓及点“关机”正常关机）后的分块扫描与 APFS Fletcher-64 校验均为 0 错误（主容器 `xid` 推进至 14318，Data 与 Update 卷干净卸载），Data 卷上的崩溃报告已能离线提取（**实机**）。但本仓库每帧 CPU 显示拷贝耗时 0.36 到 0.40 秒（每秒约 2.5 到 3 帧），实机上尚未运行温度传感器与调频驱动，拖动滚动条会触发 AppKit 主动中止。
- **每个新内核上机前都有完整的 1200 秒 QEMU 完整系统运行。** 早先的上机 14 到 17 是在没有完整的 QEMU 完整系统运行、由用户逐包放弃这一条的前提下启动的，那些完整运行后来都已经补上并通过。详见[第 5 节](#5-验证上的缺口)。

| 标记 | 含义 |
| --- | --- |
| **实机** | 平板上的录像、照片、二维码读数或从实机分块扫描提取的崩溃报告 |

| **CI** | GitHub Actions 的编译和链接通过，没有运行过 |
| **离线** | 读源码、反汇编、主机测试，没有在目标环境运行过 |

## 2. 归档时遗留的问题（多项在上游 UniXNU-sheng 已有实现）

1. **缺少实机温控与动态调频（DCVS），且显示拷贝限制了桌面帧率**：
   - **实机上未运行温度读取和温控**：已上机内核还没有温度传感器（TSENS）驱动，只能在发启动命令前从安卓读一次温度，运行中没有超温降频或保护关机。芯片硬件过温复位和 CPU 硬件限频（LMh）在 macOS 下是否起作用**未查**。（本地分支已写好 TSENS 温控、CPU/GPU 调频与有序停机并通过主机测试与 QEMU 验证，因项目归档未再上机；上游 `UniXNU-sheng` 已有 CPU/GPU 动态调频与温控代码。）
   - **实机上未启用 CPU/GPU 动态调频**：已上机包中 GPU 固定在启动参数设定的第 4 档 401 MHz（打包器接受 2 到 6 档，即 295 到 550 MHz，默认第 1 档为 220 MHz；投票同时设定 GPU 工作时的 DDR 下限）；CPU 固定在 bootloader 留下的频率（三组核心约 1670、2707、2956 MHz，L3 投票 12 档即 1574 MHz）。
   - **当前桌面帧率瓶颈在 CPU 显示拷贝，不在 GPU**：上机 43 单命令环下客户端等 GPU fence 平均每次仅约 1.5 毫秒，而显示驱动每帧读取画面、和上一帧比较并写出变化行要花 0.36 到 0.40 秒（大多数采样帧读取和比较 24.8 MB 表面像素花 330 到 368 毫秒、约 75 MB/s，仅两个采样帧在 52 到 55 毫秒内完成了读取比较并写出 223 行、读取速率至少约 475 MB/s，每秒约 2.5 到 3 帧，**实机**）。源码复核确认显示驱动已用 `kIOMapWriteCombineCache` 请求映射启动帧缓冲（XNU 仅在物理地址属于已登记 DRAM 区间时才赋予写合并属性，**离线**），**推断**慢帧耗时的主因是读到了不可缓存映射的表面页。（上游 `UniXNU-sheng` 已采用 GPU 复制与实验性显示控制器直接扫描输出。）
2. **拖动或点击滚动条导致应用崩溃（内核缺少 work interval 支持）**：
   - 在 Recovery 和正式系统（系统设置、通用设置扩展、聚焦搜索 Spotlight）里拖动或点击滚动条都会稳定触发应用崩溃（**实机**）。
   - 从实机 Data 卷提取的 `.ips` 崩溃报告显示调用链为：`-[NSScroller mouseDown:]` → `trackKnob:` → `-[NSScrollView _informDelegateWillStartLiveScroll]` → `NSUpdateCyclePerfSectionRegulationBegin` → AppKit `PerfRegulatorStart`，最后主动 `abort`，报错原文为 `Failed to create performance regulator work interval (error %i).`（报告里 `%i` 未展开，**实机**）。上游 `UniXNU` 主仓库已有对应的 work interval 内核补丁。
3. **Wi-Fi 第 5 级结果未知、本仓库无无线协议栈；蓝牙未接通**：
   - 第 4 级（上机 23）的 SMMU 不支持地址翻译自检（ATOS），DMA 窗口的地址翻译**没有验证过**；第 5 级（上机 26）执行了芯片上电和 boot loader 门铃，无卡住无 panic，但结果行要等芯片报“就绪”之后才打印，那时图形界面已接管屏幕，所以**第 5 级结果未知**（**实机**）。
   - 本仓库的 Wi-Fi 驱动后面没有无线协议栈，连不上任何网络；蓝牙只跑过第 1 级只读引脚和时钟。（上游 `UniXNU-sheng` 在 macOS 27.3 上已跑通 Wi-Fi 联网、DHCP 与收发数据。）
4. **键盘保护套第 3 级电压投票在实机未完成**：
   - 第 3 级（上机 28）第一次通过 RPMh 投 L12B 1.8 V、L13B 3000 mV，给 L12B 的投票在 50 毫秒内没收到完成信号，驱动按设计停下（L13B 未投，无 I²C 通信）；13 秒后发生内核锁等待超时 panic（与无键盘驱动时的上机 03、45 特征相同，是否有因果关系**未确定**，**实机**）。
   - **推断**原因是投票前没打开那个命令通道（TCS 2）的完成中断；打开中断并校验 PMIC 状态的修复已在本地分支写好并通过主机测试与 QEMU 验证（**离线** / **QEMU**），因项目归档未再上机。（上游 `UniXNU-sheng` 在 macOS 27.3 上已验证键盘保护套按键与触摸板指针可用。）
5. **其他遗留问题**：
   - **照片应用（Photos）崩溃**：打开照片应用在欢迎页之后退出，实机提取的崩溃报告显示在 `PXGMetalRenderer _setupMetalIfNeeded` 下调用 `PXGMetalTextureConverter createTextureFromCGImage` / `_createTransparentTexture` 时，`PhotosUIFoundation` 的 `PXCreateContext` 触发未捕获的断言异常（**实机**）；**推断**是为纹理创建位图上下文失败，可能缺少某项 GPU 插件能力。
   - **Safari 图标不显示**：离线检查确认所使用的 26.5 系统镜像从未安装 AppOS cryptex，指向 `/System/Cryptexes/App` 的 17 个符号链接（含 `Safari.app`）悬空（**离线**）。（上游 27.3 方案已将 AppOS cryptex 作为独立窗口挂载。）
   - **桌面右上角不显示硬盘图标、设置助理网络页转圈**：选“我的电脑不接入互联网”后左下角一直转圈、“继续”灰显（已通过关闭 `MiniBuddyLaunch` 偏好跳过设置助理），原因均未查清。
   - **双命令环下打开 App Store 时 GPU 挂起**：上机 42 使用两个命令环时，点开 App Store 触发挂起诊断 panic（命令处理器停在第二个环的 `CP_BLIT` 上，此前有一次切环超时，无 SMMU 故障，**实机**）；改用单命令环（`sheng-gpu-preempt=0`）后未再复现。
   - **屏幕交接时偶发内核锁等待超时 panic**：上机 03、28、45 各出现一次（`wait_while_equals32 ... timeout ... @locks.c:959`，约 0.655 秒超时，发生在 `Display on` 刚打印、WindowServer 接管屏幕前，**实机**），持有锁的线程未查明。
   - **带 Metal 插件偶发慢启动**：上机 21、33 从内核开始到 WindowServer 接管屏幕约 104 秒（正常为 22 到 33 秒），慢启动时 CPU 频率正常，变慢从 `launchd` 启动后开始（**实机**），原因未查清。
   - **后台服务崩溃循环**：实机提取报告显示 `mobileactivationd`（`EXC_BREAKPOINT`）和 `apsd`（未捕获异常中止）约每 10 秒崩溃一次，与 QEMU 中一致（**实机**）。
   - **触摸点击菜单项偶被当成拖动**：按下到抬起之间手指轻微移动会让指针坐标变化，导致菜单项把手指点击当成拖动；在上机 49、50 中，从苹果菜单点“重启”和“关机”均已验证成功，用电源键（映射为回车）选择“关于本机”也能正常打开窗口，确认应用和菜单功能本身正常，仅触摸轻点需加位移阈值（**实机**）。
   - **外设与功能缺口**：本仓库中 USB（第 2 级以上）、声音、电池状态、亮度调节、睡眠都还不能用；没有 macOS 统一日志（`tracev3`）离线解析工具。

## 3. 按功能区域

分级沿用 [UniXNU 设备记录](https://unixnu.com/porting/records)的写法：`planned`（只有计划）、`implemented`（有实现，有源码依据）、`host-verified`（在主机或 QEMU 里验证）、`device-verified`（在平板上验证）。同一区域里不同的部分可能处在不同级别，所以“限制”一栏写明范围。

| --- | --- | --- | --- |
| 配置和构建 | `device-verified` | 内核由 CI 构建，在平板上启动；也可以在 macOS 上用 Xcode 27.2 本机构建（**实机**） | 构建输入见 [ci.md](ci.md)。本机构建的内核与同一源码的 CI 内核不逐字节相同（工具链版本不同），按新内核处理，各自过门槛 |

## 4. 平板上运行过的内容和范围

- 每次启动都是 `fastboot boot`，内核镜像只进内存，不刷写启动或固件分区。每次启动、TWRP 分块扫描或分区写入都由仓库主人单独批准。
- 存储有两种运行方式，均已在实机验证：
  - **内存覆盖层模式**：运行期写入进内存（含 4096 MiB 独立页池模式），关机即丢；
  - **持久写盘模式（`native-ufs-root-writes=1`）**：写入由驱动边界检查严格限制在 `macossystem` 分区的 OS 窗口内，窗口外（含 `SHNGROOT` 头块、GPT、`macosroot`）只读不动；上机前已做基准分块扫描，每次上机后通过 TWRP 只读分块扫描与离线 APFS 校验核对，随时可只重写变化的 8 MiB 块还原到基准状态。
- 驱动默认全部关闭，只在启动参数里显式打开。
- 实机已跑过的最高级别：触摸驱动第 1 到 4 级；GPU 第 1 到 9 级及带 Metal 插件的完整桌面（含 IO 一致缓冲、401 MHz、单命令环、无状态条持久模式）；RTC 第 2 级；PSCI 复位与关机钩子；内存读数器带宽测量阶段；Wi-Fi 第 1 到 5 级；键盘保护套第 1 到 3 级；其余新驱动（USB、ADSP/电池、背光）只跑过第 1 级只读快照。
- 带 Metal 插件的包在苹果原有的信任缓存条目之外，加了插件的两个 CDHash，并把 `lp-sip0` 设为 2；普通完整系统包不变。

## 5. 验证上的缺口

- **新内核的 QEMU 验证（已满足）**：2026-11-10 晚至 11-11 凌晨上平板的每个新内核（包括 GPU 拷贝路径内核和覆盖层/持久写内核），上机前都有一次完整的 1200 秒 QEMU 完整系统运行，没有 panic，镜像没变；新显示代码的“只拷变化的行”模式也单独在 QEMU 里跑过一次，同样干净（**QEMU**）。（早先上机 14 到 17 曾在用户逐包放弃该条的前提下启动，完整的 1200 秒运行后来都已补跑通过。）
- **持久写路径的离线与实机双重验证**：由于 QEMU 使用 VirtIO 块设备而不走 `NativeUfs`，持久写路径在首次上机前先完成了离线边界审查与 21 项故障注入变异测试（抓获 20 项，1 项在未打开窗口时无行为差异），并在每次实机持久启动后通过 TWRP 全量分块哈希扫描和离线 APFS Fletcher-64 校验验证（**离线** + **实机**）。
- **观察工具修复**：原来运行到时间上限时，如果虚拟机正好停在用户态，最后一次读内核数据就会失败。现在观察工具会先让虚拟机短暂运行到内核态再读取，验收条件没有改（**离线** / **QEMU**）。
- **QEMU 里 `opendirectoryd` 的偶发 panic**：`opendirectoryd` 打开 `/Search` 或 `/Local/Default` 失败时会触发用户态 panic（`panic_on_crash_disabled` 挡不住它）。在客户机日志读得到的运行里，每次都有 1 到 5 次“重连 5 秒超时”，之后进程重启并成功；不同的只是结局，有时是重启，有时是 panic，原因没有查清（**QEMU** / **离线**）。出现该 panic 的运行均重跑，不作为证据。平板上没有见过这种 panic。
- **未上机的本地后续分支**：2026-11-11 在本地分支编写并通过主机测试与 QEMU 验证的温控与调频、显示拷贝分段诊断与源表面缓存别名、Wi-Fi 第 5/6 级与键盘电源轨完成中断修复及文件日志等候选包，因项目归档并转向参考上游更快的实现而未再上机或推送。
